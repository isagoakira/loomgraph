## 核心判断

当前产品需要把组织单位从“一个个同规格节点”提升到“具有明确分工、层级和局部编排规则的分组”。每个分组内部可以是思维分支、执行流程、连续文字或图文混排。画布负责让不同信息层次逐级可见，并对实际显示的内容维护空间；不能靠不断增加入口、把全量内容缩小或让用户反复整理来承担这些工作。

这里有三个需要分别处理的问题：

- **结构范围**：正在看整个项目、哪一组内容、还是某一组的子结构？
- **内容详略**：当前对象只显示结论，还是展开解释、例子和证据？
- **观看尺度**：把这片平面放大或缩小多少？

这三个维度可以组合，但界面必须让结果可预测。同一分组的结构展开、同一对象的正文展开和整图缩放不能混成同一种“展开”。

**本轮已确认决定 D018（2026-10-04）**：用户选择“默认持续维护局部排版”。新增内容、文字变高或展开结构时自动维护当前分组，保留手工固定位置；跨组的大调整另行预览。本条只确认自动排版的介入时机，不等于用户已确认本文全部候选设计。

## 先核对当前产品的问题

| 问题 | 已取得的证据 | 产品含义 |
| --- | --- | --- |
| 层级入口混杂 | 源码中 scope、density、intent、正文定位、单卡 disclosure 各自存在；顶部把多类入口连续排列 | 用户需要记住内部模式，才能理解某次点击会显示什么 |

| 详略缺少分工 | 完整实体卡、从正文抽取的要点、独立图解和自由正文可以一起显示；现场 AX 中同一句结论也出现在要点里 | 多个载体可能重复解释，重要性却相同，增加阅读负担 |
| 展开占位尚不能视为可靠的视觉约束 | 来源几何、HTML 自动高度、observer 测量、临时浏览几何和轴对齐碰撞盒是不同环节 | 支持测量不等于最终显示无碰撞；需要覆盖展开、收起、旋转和固定约束的验收 |
| 当前窗口阅读受阻 | 新截图中右侧概念列被裁切，底部工具区遮住正文；图解和正文以 50% 比例显示 | “都放进画布”没有解决“当前读得清楚”；可用视口也必须参加布局 |
| Harness 与显示策略尚未形成同一个回路 | harness 构造有界上下文，但不统一驱动画布范围、密度和内容分工 | prompt 写得再完整，也不能代替显示层的组织规则 |

不把隐藏的 native baseline 与可见 SVG 同时存在，直接描述成“重复画了两套线”；是否出现实际重线、穿字或 hit area 拦截，需要相应截图和交互证据。

## 原始研究与排版依据

### 总览是不同层次的信息

Shneiderman 的 *The Eyes Have It*（1996）提出 “overview first, zoom and filter, then details-on-demand”，并把 relate、history、extract 也列为用户任务。原文明确称这只是设计起点，且树与网络支持的结构任务不同。[T1]

**本项目的推论**：陌生项目的总览应该说明各分组的分工和主要关系；回到已有工作时可以恢复原位置。总览不应机械塞进所有正文，也不必把每个用户动作强行变成先返回总览。

Pad++（Bederson 与 Hollan，1994）把 semantic zoom 描述为：拉远时看到不同的表示，而不是同一个对象缩小后的版本；表示也可依据语义与任务而改变。[T2]

**本项目的推论**：项目尺度显示分组摘要与接口，工作尺度显示局部结构，阅读尺度显示当前解释。关键标题、结论和异常仍应可识别。自动变化应保留用户显式展开的内容与当前位置，避免跨过缩放阈值时反复闪变。具体切换规则仍需原型验证。

### 二维关系和段落阅读分别处理

W3C 的 Reflow 说明指出，左右移动才能逐行读文字会增加阅读负担；二维地图、图解等可以保留二维布局，但其中的文字内容仍需考虑 reflow。[T3]

**本项目的推论**：保留同一二维画布；每段正文以可读栏宽换行，尽量不要求用户左右追踪一整行。图解可横向延展，正文可沿阅读方向延伸；这不要求创建一个独立的文档阅读页面。

W3C Text Spacing 的关注点是：用户改变字距、行距等后，不丢内容、不发生不可读的重叠。它不是要求作者默认使用其中所有数值；canvas 文本与 HTML 文本的适用情况也不同。[T4]

**本项目的推论**：字号、行距、段落间隔、列表缩进和字体变化都应纳入实际测量，不能只靠文本长度估计高度。中文具体字号和栏宽应在真实窗口中验证，不将英文字符数或某个经验行距作为普适规范。

不在本轮提出“人只能看 5–7 个节点”等硬上限。画面预算取决于任务、熟悉程度、节点内容和可用窗口，应通过具体阅读任务检验。

## 建议采用的产品逻辑

以下是待讨论设计，不是已实现功能。

### 1. 分组成为主要组织单位

一个分组负责回答一个问题或完成一项可检查的交付。它有可读标题、一句结论或当前状态、子内容、内部关系和与其他分组的接口。

分组不等于画一个大框：概念讲解可以只用标题、留白和分支线建立归属；密集条目、任务阶段和研究对照可以用轻边界。只有边界承担了区分作用才显示。

阅读组织可以具有父子层级；知识关系、执行依赖、数据流和证据引用分别保留语义。同一概念可以出现在多处，引用共同身份；不能因为分组是树，就把完整关系网改成单父树。

层级不限定为固定三层。产品至少需要清楚支持项目骨架、当前分组和子结构这些尺度，并允许继续深入。

### 2. 每次展开有明确的信息变化

| 动作 | 应出现的信息 | 应保留的上下文 |
| --- | --- | --- |
| 展开分组 | 下一层子结构与其主要关系 | 父组的问题、结论或状态，进入位置 |
| 展开内容 | 当前对象的解释、例子、证据或复现细则 | 原标题、核心结论和关联对象 |
| 聚焦局部 | 同一平面中当前工作区域的可读呈现 | 项目位置、返回入口，必要邻接与远处关系提示 |
| 缩放整图 | 改变观看尺度，必要时简化远景表示 | 对象身份、用户显式展开选择和空间定位 |

分组折叠后要有信息充分的摘要。知识分组显示“本组解释了什么”，任务分组显示“目前做到哪里、哪里受阻”。折叠不能只留下一个名字，也不能把失败藏进平均完成度。

点击后的变化优先发生在原位置附近。大内容可聚焦同一平面中的局部；模态弹窗不承担默认阅读。折叠入口和正文细节入口必须在语义上区分，避免让用户猜。

### 3. 详略按表达作用分配

默认可见内容应足够回答当前问题；必要概念在使用处可直接找回。细节只在确实增加机制解释、例子、证据或操作依据时展开。

| 载体 | 主要作用 |
| --- | --- |
| 标题 | 告诉读者这是哪一块、解决什么问题 |
| 核心结论 | 给出这一块应带走的判断 |
| 图解/局部结构 | 展示分工、步骤、输入输出、分支与对照 |
| 正文 | 解释为什么、举例，并承接前后内容 |
| 研究细则 | 参数、条件、定量结果、消融、来源和局限 |

不强制每个模块都显示“定义、要点、输入输出、证据状态”整套模板。共享的来源说明可放在分组层；当某项材料的证据性质不同，才在局部明确标记。证据仍保留完整身份与查询入口。

原子化的标准是“能被独立引用、复用或改变”，不是“能拆成一个名词”。一个定义及理解它所需的短解释应保持在一起；流程步骤和证据比较则采用适合自身任务的单位。

### 4. 自动排版维护实际占位

自动布局的对象包括正文、图解、展开内容、标签、标题和可见操作区。子内容变高，父分组的占位也要增长；相邻分组依据增长后的整体边界避让。

建议顺序是：确定内容宽度与呈现密度 → 测量实际显示尺寸 → 编排组内结构 → 汇总分组边界 → 避让邻组 → 布线 → 核对当前可用视口。布局引擎负责它擅长的关系排列，产品层负责阅读、固定约束和最终可见结果。

展开优先局部让位；状态更新优先改变文字和标识。不能因一个任务状态变化就整图重排。当前阅读对象保持屏幕锚点，收起后尽量恢复邻居原有关系；需要记录可测的偏移，而不是只声称“稳定”。

手动固定的位置参加约束。若固定内容导致无空间可用，应给出具体冲突或可选局部整理方案；不能同时承诺“绝不移动所有固定块”和“任何展开都在原地无碰撞”。手工构图中用户有意叠放的元素，可以声明意图；自动组织中的非意图文字覆盖应视为失败。

浏览展开产生的是临时显示布局。用户明确应用整理或调整几何时，再保存为内容变更；不能让一次阅读展开污染项目版本历史。

### 5. 连线有局部责任和跨组接口

组内思维分支用归属关系表达，流程用有方向的步骤/数据关系表达；交叉引用按需显现。颜色和样式辅助辨认，不能代替关系含义。

跨组的长程关系默认在组边界汇总为带含义的接口/引用，沿接口可定位原始关系。查看特定关系或整体工作流时，可显式显示跨组连接；远关系不是被删除。局部概念回顾应放在使用处，不能只给一条跨屏长线让读者去找定义。

### 6. 理解与监控改变重点，共用结构

| 主导任务 | 默认突出 | 按需展开 |
| --- | --- | --- |
| 理解信息 | 当前问题、必要定义、局部图解、主干解释、下一步承接 | 完整证明、定量证据、复现与局限 |
| 监控工作 | 当前阶段、实际状态、阻碍、下一项交付、更新时间 | 日志、运行回执、参数、实现机制 |
| 混合工作 | 局部指定主导任务；状态贴在相应工作对象旁 | 同一区域的解释与运行证据 |

切换主导重点不应产生一套全新的物理布局；结构位置和身份保持可追踪。任务状态必须说明来源与新鲜度；内容编辑完成、请求入队与真实执行完成分别呈现。进度汇总按实际任务身份去重。

## 对 Agent Harness 的要求

Harness 应先生成组织方案，再填内容，最后验证显示；prompt 不应直接从论文段落推导出一堆同规格卡片。

1. **确定读者/任务**：本次是学习、研究复现、任务监控还是混合？这一局部要回答什么？
2. **划分分工和前提**：每组承担什么，哪些概念必须在使用处出现，哪些只需回顾？
3. **选择局部形式**：线性步骤、思维分支、对照、反馈回路、连续文字分别用适合的组织形式。
4. **决定详略与载体**：保留主干；让图解、正文和证据互相补充，审查重复解释。
5. **获得布局事实**：读取实际可用视口、显示层级、测量尺寸、固定约束和当前阅读锚点；不能仅靠 token/节点数量决定密度。
6. **局部增量和验收**：保存稳定身份、前后语义与变更依据；确认实际显示的可读性与空间关系，不能只检查字段齐全。

来源内容、任务状态、阅读顺序、视觉层级与执行依赖各有责任。图上的位置不自动生成业务语义；画面暂时省略内容也不意味着 Agent 已读完这些内容。

## 用现有论文样例讨论，而不重新堆一张大图

建议先只讨论“分类索引与双记忆”这个局部：

- 默认由一个局部机制图解释分类索引 → 子类别 → F/R 分工；旁边或下方用短正文说明两份手册为什么不同。
- F、R 的名称及必要定义靠近各自位置。点击细则后，分别出现一个具体检查例或校准例，而不是再复制同一段摘要。
- “用于新预测”的承接作为该组出口；另一组的预测流程保持可定位，并在使用处简短回顾 F/R 的含义。
- 参数、消融和复现条件放在可就地展开的研究分组里，保持与方法对象的联系；不抢占首次理解的主干。

再用一个真实任务阶段做对照，验证同一组织体系能否表达状态、阻碍和子流程。不能以论文样例可读，就断言任务监控也完成。

## 已讨论的取舍与后续讨论顺序

本轮已经讨论并确定：**自动排版默认持续维护局部**。

用户选择的行为是，在插入、正文尺寸变化和结构展开时持续维护当前分组，保留手工固定位置；跨组大调整另行预览。阅读锚点、具体展开恢复规则和布局冲突提示仍属于待验证的设计。未采用“只在点击整理时重排”作为默认体验。

后续再讨论层级展开时如何显示相邻组、长正文的呈现边界和临时展开的恢复行为。先验证规则，再决定控件位置和视觉样式，不以增加更多模式作为默认解法。
